# OPERATIONS — נספח רגולציה ותפעול (WP-21)

**עודכן:** 2026-08-31 · **סטטוס:** טיוטה לאישור הלקוח

המסמך הסוגר של v1. מרכז את ההיבטים התפעוליים, המשפטיים והרגולטוריים של הפעלת המערכת
בפרודקשן עבור מטפלת יחידה (נופר כהן, יקנעם). כל סעיף מסתיים ב**החלטה** ובפעולות פתוחות.
פעולות שדורשות קוד הופכות ל-WP (ראה §10).

> **הקשר משפטי — לא ייעוץ משפטי.** ההמלצות כאן הן פרקטיות ומבוססות על המצב לאוגוסט 2026.
> לפני עלייה לאוויר עם מטופלים אמיתיים — מומלץ אישור עו״ד המתמחה בהגנת הפרטיות ובדין הבריאות.

## 1. גיבוי ותרגיל שחזור

**מה מגובה:**

| נכס | מנגנון | תדירות | שמירה |
|-----|--------|--------|-------|
| Postgres (Neon) | Point-in-Time Restore מובנה של Neon | רציף (WAL) | 7 ימים ב-Free; יש להגדיל ל-**30 יום** בתוכנית בתשלום לפני פרודקשן |
| Postgres — snapshot לוגי | `pg_dump` שבועי ל-Blob/מקומי | שבועי | 90 יום, 4 עותקים חודשיים |
| קבצים (Vercel Blob) | אין versioning מובנה | — | ראה פעולה פתוחה |
| קוד + מיגרציות | Git (GitHub) | בכל push | ללא הגבלה |
| משתני סביבה | מתועדים ב-Vault/מנהל סיסמאות של הלקוח (לא ב-git) | ידני בכל שינוי | — |

**תרגיל שחזור (Restore drill) — להריץ פעם ברבעון:**

1. ב-Neon → Branches → צור branch מ-PITR לנקודת זמן לפני 24 שעות.
2. `DATABASE_URL` של ה-branch → סביבת staging נפרדת ב-Vercel (Preview).
3. אימות: התחברות מטפלת, פתיחת 3 תיקי מטופל, בדיקת `/t/audit` שהרשומות שלמות, הורדת מסמך.
4. השוואת `count(*)` על הטבלאות המרכזיות מול הפרודקשן (סטייה מוסברת רק ב-24ש' האחרונות).
5. תיעוד: תאריך, משך, מי ביצע, ממצאים — בטבלת "יומן תרגילים" בתחתית המסמך.

**pg_dump שבועי (עד לאוטומציה):**
```bash
pg_dump "$DATABASE_URL_UNPOOLED" -Fc -f "nofar-$(date +%Y%m%d).dump"
```

**החלטה:** PITR של Neon הוא קו ההגנה הראשון. חובה: (א) שדרוג שמירת ה-PITR ל-30 יום, (ב) `pg_dump`
שבועי אוטומטי, (ג) גיבוי Blob (ראה §10 — WP-23). תרגיל שחזור רבעוני עם תיעוד.

**פעולות פתוחות ללקוח:**
- לשדרג תוכנית Neon כדי לקבל 30 יום PITR.
- להחליט היכן נשמרים ה-`pg_dump` (Google Drive פרטי / דיסק מוצפן).

## 2. Monitoring וזמינות

| שכבה | כלי | מה בודקים |
|------|-----|-----------|
| פריסה + פונקציות | Vercel → Observability / Logs | שגיאות 5xx, זמני תגובה, כשלי build |
| DB | Neon → Monitoring | חיבורים פעילים, שימוש באחסון, זמן שאילתה |
| דוא״ל | Resend → Logs | כשלי מסירה, bounce, תלונות spam |
| Uptime חיצוני | UptimeRobot / Better Uptime (חינם) על `/api/version` | האתר באוויר; התראה למייל/טלפון |
| חותמת גרסה | `GET /api/version` | לוודא שהדחיפה האחרונה עלתה (shortSha מול `main`) |

**מה נחשב אירוע:** האתר לא נגיש > 5 דק׳ · שגיאות 5xx על `/t/*` או `/p/*` · כשל מסירת דוא״ל
של הזמנה/איפוס · חריגה חריגה בשימוש DB/Blob (עלול להעיד על ניצול לרעה).

**החלטה:** `fail-open` בשכבות דוא״ל, audit והתראות אומץ במכוון (ADR-018/020/021) — כשל בהן לא מפיל
פעולה קלינית. לכן ה-monitoring צריך לתפוס אותם: מעקב שבועי אחר Resend Logs + Vercel Logs.

**פעולות פתוחות ללקוח:** להקים UptimeRobot על `/api/version` עם התראה לטלפון.

## 4. תגובה לאירוע אבטחה (Incident Response)

**עקרון:** מטופל שנחשף למידע של מטופל אחר = אירוע חמור (כלל הזהב). כל חשד → לפעול, לא להמתין.

**צעדים:**

1. **הכלה (0–1 שעה).** לזהות את ההיקף מ-`/t/audit` (מי, מה, מתי, איזה מטופל). אם דליפה פעילה —
   להשבית זמנית: ב-Vercel אפשר לבטל את הפריסה האחרונה (Rollback) או להעביר את הפרויקט ל-Password
   Protection.
2. **ראיות.** לייצא את הרלוונטי מ-`audit_log` (append-only, לא ניתן לשינוי) + Vercel Logs לתקופה.
3. **תיקון.** לזהות שורש (bug ב-scoping guard / חשיפת endpoint / זליגת token) → תיקון + בדיקת
   `tests/isolation` שנכשלת על התרחיש → פריסה.
4. **הערכת חובת דיווח.** לפי חוק הגנת הפרטיות (ותיקון 13, ר׳ §8): אירוע אבטחה חמור מחייב דיווח
   לרשות להגנת הפרטיות, ובמקרים מסוימים למטופלים המושפעים. **להתייעץ עם עו״ד תוך 24 שעות.**
5. **תחקיר.** לתעד: ציר זמן, שורש, תיקון, מה מונע הישנות. להוסיף בדיקת בידוד קבועה.

**אנשי קשר (למילוי ע״י הלקוח):**
- עו״ד פרטיות: ______
- איש קשר טכני (מתחזק): ______
- Vercel support / Neon support: דרך הדשבורד (תוכנית Pro = תגובה מהירה יותר).

**החלטה:** ה-audit log ה-append-only (trigger ב-DB) הוא הכלי המרכזי לתחקיר — לוודא ששמירתו
(730 יום) לא נפגעת ע״י גיזום מוקדם מדי.

## 5. DPA וספקי משנה (Sub-processors)

המערכת מעבירה מידע אישי ורפואי לספקים הבאים. לכל אחד יש להסדיר **הסכם עיבוד נתונים (DPA)**
ולתעד את מיקום המידע:

| ספק | תפקיד | מיקום מידע | DPA | הערות |
|-----|-------|-----------|-----|-------|
| **Vercel** | אירוח, הרצת קוד, לוגים | Functions: **`fra1` (פרנקפורט)** — נכפה ב-`vercel.json` (`regions`) מ-WP-23. Blob: **IAD1 (ארה״ב)** — פתוח | Vercel DPA סטנדרטי — לאשר בחשבון | Function Region ב-Dashboard מומלץ גם הוא = Frankfurt (חגורה+שלייקס). Blob EU — ר׳ §10 |
| **Neon** | Postgres | **פרנקפורט (`eu-central-1`)** ✓ | Neon DPA — לאשר | מיקום EU תקין |
| **Resend** | דוא״ל טרנזקציוני (הזמנה/איפוס/תזכורת) | ארה״ב (Resend) + ספק תשתית | Resend DPA — לאשר | הדוא״ל מכיל שם פרטי + קישור; לא מכיל מידע רפואי |
| **GitHub** | קוד + CI (ללא מידע מטופל) | ארה״ב | לא נדרש DPA — אין PII בקוד | לוודא שאין secrets/PII ב-repo |

**מיקום מידע — סיכום:** הליבה (DB) ב-EU. **חריג פתוח: קבצי Blob ב-IAD1 (ארה״ב).** המשמעות:
העברת מידע רפואי לחו״ל — מצריכה בסיס חוקי (הסכמת המטופל קיימת דרך `consent.data_transfer_abroad`,
אך עדיף לתקן את מיקום ה-Blob).

**החלטה:**
1. פונקציות Vercel — **נכפו ל-`fra1` ב-`vercel.json`** (WP-23). לוודא ב-Dashboard → Settings → Functions → Function Region = Frankfurt.
2. Blob — לבדוק אפשרות אזור EU; אם אין, לשקול S3 תואם באזור פרנקפורט. עד אז — לוודא שהסכמת
   `data_transfer_abroad` נאספת מכל מטופל (השדה קיים ב-WP-10).
3. לאשר את שלושת ה-DPAs (Vercel/Neon/Resend) — פעולה חד-פעמית של הלקוח.

## 6. שמירת מידע מול מחיקה

### מדיניות שמירה

| סוג מידע | תקופת שמירה | בסיס |
|----------|-------------|------|
| רשומה רפואית (תיק, מפגשים, תוכניות, שאלונים, מסמכים) | **7 שנים** מתום הטיפול | נוהג מקצועי + דרישות רשומה רפואית |
| Audit log | **שנתיים** (`AUDIT_RETENTION_DAYS = 730`) | איזון בין יכולת תחקיר לצמצום מידע |
| הודעות (`message`) | 7 שנים עם התיק | חלק מהתיעוד הקליני |
| נתוני התחברות (`session`, `login_attempt`) | `session` — עד לפקיעה; `login_attempt` — 90 יום | תפעולי בלבד |
| הזמנות/איפוסים שנוצלו או פגו | 90 יום | תפעולי |

### מחיקה — anonymize + lock, לא hard-delete

מטופל שמבקש "מחיקה" / סיום קשר: **לא** מוחקים את הרשומה (חובת שמירה 7 שנים גוברת), אלא:

1. `patient.status = 'inactive'` + חסימת גישת המטופל (ביטול ה-`user` שלו).
2. אנונימיזציה של שדות מזהים שאינם נדרשים לרשומה (טלפון, דוא״ל, כתובת) — לאחר 7 שנים.
3. שמירת התוכן הקליני עד תום 7 השנים, ואז מחיקה/אנונימיזציה מלאה.
4. פעולת ה-anonymize עצמה נרשמת ב-audit.

**מצב נוכחי:** אין עדיין מסך/סקריפט למחיקה מבוקרת. `purgeOldAudit` קיים (ADR-018) אך **לא
מתוזמן**. שני אלה → §10 (WP-23, WP-25).

**החלטה:** מדיניות השמירה שלעיל מאושרת עקרונית. המימוש (anonymize flow + cron לגיזום audit)
נדחה ל-WP-ים ייעודיים ולא חוסם v1 — v1 רק **צובר** מידע ולא מוחק, וזה הצד הבטוח.

## 7. המשכיות עסקית — אם המטפלת מושבתת

**שחזור גישה ל-2FA:** אין recovery codes ב-v1. אם המטפלת איבדה את אפליקציית האימות —
`UPDATE "user" SET totp_secret=NULL, totp_enabled_at=NULL WHERE email='<המייל>';` דרך Neon SQL Editor
(איש האמון עם גישת ה-DB), ואז כניסה עם סיסמה בלבד והרשמה מחדש ב-`/t/settings`.


תרחיש: נופר חולה / לא זמינה לתקופה, ומטופלים צריכים גישה למידע שלהם או להעברת טיפול.

| נכס | מי צריך גישה | פתרון v1 |
|-----|--------------|----------|
| מרחב המטופל (`/p`) | המטופלים עצמם | ממשיך לעבוד — לא תלוי בנוכחות המטפלת |
| תיקים קליניים (`/t`) | מטפל/ת מחליף/ה או המטופל | **ידני:** ייצוא `pg_dump` + מסמכים, מסירה מאובטחת לגורם מוסמך לפי בקשת המטופל |
| חשבון המטפלת | — | **מפתח שחזור:** סיסמת המטפלת + גישת ה-DB נשמרים במעטפה סגורה / כספת דיגיטלית משותפת עם איש אמון (עו״ד / בן משפחה) |
| דומיין + DNS + Vercel/Neon | מתחזק טכני | פרטי החשבונות מתועדים אצל איש האמון |

**החלטה:** אין ב-v1 מנגנון "delegate access" בתוך המערכת (מטפל יחיד לפי הגדרה). ההמשכיות מבוססת
על **תיק חירום** מחוץ למערכת: מסמך עם פרטי גישה לכל הספקים + נוהל, אצל איש אמון. יש להכין אותו
לפני עליית מטופלים אמיתיים.

**פעולה פתוחה ללקוח:** להכין "תיק חירום" (פרטי גישה + נוהל) ולמסור לאיש אמון.

## 8. חובת רישום מאגר מידע — תיקון 13 לחוק הגנת הפרטיות

תיקון 13 לחוק הגנת הפרטיות נכנס לתוקף ב-**14 באוגוסט 2025** ושינה מהותית את הדין:

- **בוטלה חובת הרישום הכללית** של מאגרי מידע ברשם. במקומה — חובת **ניהול, אבטחה ואחריותיות**,
  וסמכויות אכיפה מוגברות לרשות להגנת הפרטיות (עיצומים כספיים).
- מאגר עם **מידע רפואי** = "מידע רגיש" → חלה עליו רמת האבטחה הגבוהה בתקנות אבטחת מידע (2017):
  מסמך הגדרות מאגר, מיפוי, בקרת גישה, תיעוד (log), הצפנה בתעבורה, נוהל אירוע אבטחה, סקר סיכונים
  תקופתי, ומינוי **ממונה הגנת פרטיות (DPO)** מעל סף מסוים של נושאי מידע.
- **מינוי DPO:** חובה בין היתר ל"מי שעיסוקו העיקרי מצריך עיבוד מידע רגיש בהיקף נרחב". קליניקה של
  מטפלת יחידה עם עשרות–מאות מטופלים — **סביר שמתחת לסף "היקף נרחב"**, אך זו הערכה שדורשת אישור.

**מה כבר מיושם במערכת (מיפוי מול התקנות):**

| דרישה | מצב |
|-------|-----|
| בקרת גישה מבוססת הרשאות | Scoping Guard (ADR-016) + RBAC — כל גישה למידע מטופל מסוננת ב-scope |
| תיעוד גישה (audit trail) | `audit_log` append-only (trigger ב-DB), 730 יום — "מי, מה, מתי, איזה מטופל" |
| הצפנה בתעבורה | HTTPS בכל הנתיבים (Vercel) |
| הצפנת סיסמאות | argon2id |
| אימות חזק למנהל | סיסמה + TOTP (2FA) למטפלת |
| נעילת חשבון + rate-limit | 5/15דק' + חנק IP |
| הפרדת סביבות | production מול preview ב-Vercel |
| מזעור מידע | שדות דינמיים דרך Field Registry; לא נאסף מה שלא נדרש |

**פערים ידועים:**

| פער | חומרה | טיפול |
|-----|-------|-------|
| `totp_secret` נשמר ב-DB **ללא הצפנה at-rest** | בינונית | WP-24 (§10) |
| קבצי Blob באזור ארה״ב (העברה לחו״ל) | בינונית-גבוהה | WP-23 (§10) + הסכמת `data_transfer_abroad` |
| אין סקר סיכונים תקופתי מתועד | נמוכה ל-v1 | להריץ שנתית; תבנית בסוף המסמך |
| אין "מסמך הגדרות מאגר" פורמלי | נמוכה | המסמך הזה + `DATA_MODEL.md` + `ARCHITECTURE.md` ממלאים את רובו; לפרמל לפני מטופלים אמיתיים |
| הצפנת מידע רגיש at-rest ב-DB (מעבר לסיסמאות) | נמוכה-בינונית | Neon מצפין את האחסון; הצפנה ברמת-שדה לעמודות רפואיות = שיפור עתידי, לא חוסם |

**החלטה:**
1. **אין חובת רישום ברשם** (בוטלה בתיקון 13). יש חובת ניהול ואבטחה — רובה מיושמת (טבלה לעיל).
2. **DPO — כנראה לא נדרש** בהיקף של מטפלת יחידה, אך **חובה לאשר עם עו״ד פרטיות** לפני פרודקשן.
3. לסגור את שני הפערים הבינוניים (WP-23, WP-24) לפני קליטת מטופלים אמיתיים בהיקף.
4. לפרמל "מסמך הגדרות מאגר" (שילוב של המסמך הזה + DATA_MODEL + ARCHITECTURE) ולהחתים סקר סיכונים
   שנתי.

## 9. Data flow — לאן זורם מידע מטופל

```
מטופל/מטפלת ──HTTPS──> Vercel (Next.js, Functions)
                          │
                          ├──> Neon Postgres (פרנקפורט)   ← רשומות, audit, שדות, הודעות
                          ├──> Vercel Blob (IAD1 *)        ← קבצי מסמכים (פרטי)
                          └──> Resend (ארה״ב)              ← דוא״ל: שם פרטי + קישור בלבד
* יעד לתיקון — WP-23
```

- **אין** אנליטיקס צד-שלישי, אין tracking pixels, אין CDN חיצוני לנכסים.
- **אין** שיתוף מידע עם צד ג׳ מלבד ספקי המשנה בטבלה §5.
- Cookies: רק cookie session אחד (httpOnly, lax, sameSite) — אין cookies שיווקיים.

## 10. פעולות שדורשות מימוש → WP עתידיים

| WP | תיאור | חוסם פרודקשן עם מטופלים? |
|----|-------|--------------------------|
| **WP-23** | ✅ פונקציות Vercel ל-`fra1` (`vercel.json`). **פתוח:** Blob store באזור EU (ליצור חדש + לעדכן `BLOB_READ_WRITE_TOKEN`; קובץ הבדיקה היחיד יאבד) או S3 פרנקפורט; גיבוי Blob | Blob עדיין US → העברה לחו״ל |
| **WP-24** | הצפנת `totp_secret` at-rest (מפתח ב-env, `crypto.subtle` / libsodium) | מומלץ לפני פרודקשן |
| **WP-25** | Retention cron: `/api/cron/purge` מוגן ב-`CRON_SECRET` → `purgeOldAudit` + גיזום `login_attempt`/הזמנות פגות; הגדרת `crons` ב-`vercel.ts` | לא (v1 רק צובר) |
| **WP-26** | Anonymize + lock flow למחיקת מטופל מבוקרת (מסך + audit) | לא |
| **WP-27** | `pg_dump` שבועי אוטומטי (GitHub Action / Vercel Cron → Blob) | לא (PITR מכסה בטווח קצר) |
| **WP-22** | חומרת בידוד — סקירה סופית (`/security-review`, מעבר endpoint-by-endpoint, זיוף URL/ID ידני) | **כן** |
